## Creating Posts

The first step to adding a blog to a Jekyll site is to create a folder named `_posts` to hols all your blog posts.

### File Names and Dates

When adding regular pages you can name then anything you like, but Jekyll defines a naming scheme for blog posts:

```
YEAR-MONTH-DAY-slug.md
```

For example, to create a post dated April Fool's Day this year (2026) with the slug `april-fools` create a file named `2026-04-01-april-fools.md`.

Let's create our first blog post by adding the following to `./docs/_posts/2026-04-01-april-fools.md`:

```markdown
---
title: Some Classic April Fools
---
Over the years the BBC have done some of my very favourite April Fools gags:

* [The Spaghetti-tree Hoax](https://en.wikipedia.org/wiki/Spaghetti-tree_hoax) (1957)
* [The Flying penguin hoax](https://en.wikipedia.org/wiki/Flying_penguin_hoax) (2008) 

You can usually find coppies of these videos on YouTube, but they come and go, so good luck!
```

Build your site, and have a look in the generated `_site` folder which contains the website built by Jekyll. You'll see a new folder has been added named `2026` which contains a folder `04` which contains a folder `01` which contains our rendered blog post as `april-fools.html`.

This means that, when using Docker, the blog post can now be accessed at `http://localhost:4000/2026/04/01/april-fools.html`.

The first thing to notice is that the post has been rendered using our default layout, it contains no blog-specific information, just our post's body.

## Creating a Blog Post Layout

To render blog posts appropriately we need to add a new layout for them to our theme.

Rather than creating a top-level layout, we just need to create a nested layout that adds the blog-specific metadata into the content region of the default theme.

Jekyll actually assumes that if there's a layout named `post.html`, that that's the one it should use for blog posts. 

To create our blog post layout we simply create a new file named `./docs/_layouts/post.html` with the following initial content:

```html
---
layout: default
---
<div class="post-heading mb-5">
  <h1 class="display-1 mb-0">{{ page.title }}</h1>
  <h2 class="text-muted fw-light">{{ site.meta.author }} — {{ page.date | date: "%B %d, %Y" }}</h2>
</div>

<div class="post-body">
  {{ content }}
</div>
```

I want to draw your attention to a few things about this file.

Firstly, we use the `layout` front matter key to nest out layout inside the `default` layout. Just a reminder that Jekyll themes work like Russian nesting dolls, so what this means is that our new layout will be injected into the `default` layout (defined in `./docs/_layouts/default.html`) at the `{% raw %}{{ content }}{% endraw %}` Liquid tag.

When you create a blog post Jekyll determines that date from the filename and makes it available as the Liquid variable `page.date`. We need to format this date in a human-friendly way, so we use the Liquid `date` filter to make that conversion.

Out site already stores the author's name in the `_config.yml` file (we added it in [the previous instalment](./pbs187) to facilitate our metadata tags), so we can access it via `site.meta.author`.

To facilitate blog-post-specific styling, I wrapped both the blog post heading information and the blog post body in `<div>` tags with the classes `post-heading` and `post-body`.

Finally, I added some standard Bootstrap classes to control the look of the header.

Allow the site to re-build, and you should see our blog post now has it's title, date, and author name.

We now have blog posts that look like blog posts.

## House Keeping — Adding a Dedicated Layout for Pages

Now that we are using two taxonomies, we should update our site to have dedicated layout for both. We've already created one for blog posts, we should do the same for pages. Again, Jekyll looks for a layout named `page.html` and automatically uses it.

Our current default layout has a short-coming that we should fix for our pages — it does not support page titles properly!

At the moment, our two standard pages, `about.md` and `links.md` define their titles in unusual ways. Our pages have `title` properties defined in their front matter, but those are short one-word titles that we currently use in the nav bar, but nowhere else. This is not best practice, the `title` attribute is what Jekyll considers the canonical title, so it really should be the title we want to show people on the pages.

We can keep both our short nav bar and our longer visual tittles by using separate front matter for each.

We'll move the long title into the standard `title` key, and add a new key of our own named `short_title` for user in our nav bar. With both titles then captured in the front matter, we'll remove the unneeded leading markdown top-level header.

Edit `./docs/about.md` so the start of the file becomes:

```markdown
---
title: About this Site
short_title: About
meta:
  description: An explanation of the PBS Jekyll demo site.
---
This site is part of the Programming by Stealth tutorial and podcast series co-created by [Bart Busschots](https://www.bartb.ie/) and [Allison Sheridan](https://www.podfeet.com/). You'll find the series itself at [pbs.bartificer.net](https://pbs.bartificer.net/).
```

Next, repeat the process and edit `./docs/links.md` so the start of the file becomes:

```markdown
---
title: Useful Links
short_title: Links
meta:
  description: A list of links that might be useful when developing a Jekyll site on GitHub Pages.
---
Some links you may find useful while working with Jekyll on GitHub Pages
```

Allowing the site to re-build now will show we've created two new problems to solve:

1. The About and Links pages no longer have visible headings
2. The nav bar now has the long titles

Let's start by fixing the nav bar. Edit `./docs/_layouts/default.html` and replace the line that renders each link inside the loop with the following version (line 33):

```html
{% raw %}<a class="nav-link {%- if p.url == page.url %} active{% endif %}" {%- if p.url == page.url %} aria-current="page"{% endif %} href="{{ p.url | relative_url }}">{{ p.short_title | p.title }}</a>{% endraw %}
```

The only change is that the content of the `<a>` tag has been changed from `p.title` to `p.short_title | default p.title`.

Allow the site to re-build, and notice that the nav bar has now been corrected.

We're now ready to fix our visible heading by creating our dedicated layout for pages.

Create a file named `./docs/_layouts/page.html` with the following contents:

```html
{% raw %}---
layout: default
---
<h1 class="display-1 mb-5">{{ page.title }}</h1>

{{ content}}{% endraw %}
```

This is a very simple nested layout that inserts the page title followed by the page body into the default theme's `{% raw %}{{ content }}{% endraw %}` placeholder.

If you found all that a little hard to follow, I've tagged the final commit with all these changes as [pbs188-afterHousekeeping](https://github.com/bartificer/pbs-jekyll-demoSite/releases/tag/pbs188-afterHousekeeping).

## Adding a Blog Index

As things stand, the only way our visitors can find our blog posts is if we give them the URL to the posts. We need to add a landing page for our blog to our site.

This will be a regular page that loops over all the entries in the *posts* taxonomy and lists them.

Jekyll exposes the *posts* taxonomy through a variable named `posts`. This is a list of objects that contain the information about each post. Jekyll also, very considerately, sorts the list in reverse-chronological order for us!

We could name our landing page anything we like, but let's keep it simply and use `blog.md`.

Create a file named `./docs/blog.md` with the following content:

```markdown
{% raw %}---
title: Blog
---
This is a demo Jekyll blog, it contains nothing but nonsense 🙂

<ul>
  {% for post in site.posts %}
    <li>
      <strong>{{ post.date | date_to_string }}:</strong> <a href="{{ post.url | relative_url }}">{{ post.title }}</a>
    </li>
  {% endfor %}
</ul>{% endraw %}
```

This is simply a regular page with a Liquid loop that loops over `site.posts` to add items to a list.

## Post Summaries

Something else that might be nice to do is add a most recent post callout to the front page.

For this kind of featured link we want more than just a title, we also want a short snippet from the post. Jekyll automatically creates excerpts for each post, and by default they consist of the first paragraph. If you prefer to use the Wordpress convention of using `<!-- more -->`, you can add the following to your `_config.yml` file:

```yaml
excerpt_separator: '<!-- more -->'
```

Regardless of how you create the snippet, Jekyll stores it as **rendered HTML** (not markdown) a key named `excerpt` in the post's object.

Because Jekyll automatically sorts the `posts` list in reverse-chronological order, the newest blog post is easily available as `posts | first`.

To make our little latest post widget more re-usable, let's add it is as snippet.

Create a file named `./docs/_includes/latest_post_card.html` with the following contents:

```html
{% raw %}{%- comment %}Store the latest post in a variable{% endcomment %}
{%- assign latest_post = site.posts | first %}

{%- comment %}Build the card{% endcomment %}
<div class="card text-bg-light">
  <div class="card-header">
    Latest Blog Post — {{ latest_post.date | date: "%B %d, %Y" }}
  </div>
  <div class="card-body">
    <h1 class="card-title h5">{{ latest_post.title }}</h1>
    <p class="card-text">{{ latest_post.excerpt }}</p>
    <a href="{{ latest_post.url | relative_url }}" class="card-link">more …</a>
  </div>
</div>{% endraw %}
```

This builds a Bootstrap card using the details from the latest post.

Let's replace the sill note we added to the end of the front page for the PBS 181 challenge with our new card.

Open `./docs/index.md` , and replace the existing `{% raw %}{% include %}{% endraw %}` with this new one:

```
{% raw %}{% include latest_post_card.html %}{% endraw %}
```

Allow the site to render, and then have a look at the front page. You'll see we now have a nice little card showing the excerpt for our latest post with a link to view the full post.

## Using Categories

If your site is only using posts for some kind of a latest news feed rathe than as a full blog you don't need to worry about categories. The same might also be true if your blog is focused on a single topic, like [Daring Fireball](https://daringfireball.net), but most blogs cover more than one broad topic, so that's where categories make sense.

It is possible to define categories using the file system, but this messy, it creates multiple `_posts` folders!

For our example we're going to keep things simple and work with just two basic categories, *humour* and *science*.

If we were to do this using the file system we would need to replace our single `_posts` folder with the following two:

* `./docs/humour/_posts`
* `./docs/science/_posts`

I really don't like spreading my blog posts around like that, so I prefer to use the front matter for defining categories.

### A Note On Nested Categories

At first glance, you can also create nested categories using the file system. For example, we could create a third folder named `./docs/science/physics/_posts`, and it would get published. However, the categories will not work as you expect — your posts will not classified into a single nested category, but into two top-level categories named `science` and `physics`.

This is where Jekyll's out-of-the-box blogging features fall short of what you get with dedicated blogging platforms. Firstly, for a lot of sites, a single set of top-level categories is all that's needed, and secondly, you can implement as complex a taxonomy as you can imagine if you move from the pre-provided *posts* taxonomy to a custom taxonomy implemented as a Jekyll *collection* (a much more advanced feature beyond the scope of this instalment).

> I implemened a nested taxonomy with podcasts containing podcast epidsoides using Jekyll's collections feature on the [Let's Talk Podcasts website](https://www.lets-talk.ie/).
{: .aside} 

There are also various plugins available for adding more advanced blogging features, but they generally don't work with the standard GitHub Pages setup. Again, that doesn't mean you can't use them on GitHub, you just need to write your own GitHub action to build Jekyll rather than relying on the built-in one.

### Assigning Categories with Front Matter

If you choose not to use the file system option for categorising posts, then you add them to the post's front matter.

Because posts can be in more than one category, Jekyll will store them in a key named `categories` as an array of strings, but if you only want to assign your post to a single category (the norm!), then you can use the shortcut front matter key `category` which expects a single string.

When you create a post with the following in the front matter:

```yaml
category: science
```

Jekyll silently converts that to the following for you:

```yaml
categories: [ science ]
```

Let's add a category to our existing post.

Open `./docs/_posts/2026-04-01-april-fools.md` and update front matter to be:

```yaml
---
title: Some Classic April Fools
category: humour
---
```

We also need a post in our science category, so create a file named `./docs/_posts/2026-07-15-female-scientists.md` with the following content:

```markdown
---
title: Some Amazing Female Scientists
category: science
---
If you ask a random stranger on the street to name a female scientist you'll almost always get the same answer *Marie Curie*. She was, without a doubt, a great scientist, and indeed a female, but she's just one of countless many super scientists who happen to be female.

Why not spend some time learning a little more about:

* Computer scientists [Grace Hopper](https://en.wikipedia.org/wiki/Grace_Hopper) & [Emily Anderson](https://en.wikipedia.org/wiki/Emily_Anderson) (🎧 [Listen to her story on the Irish History Podcast](https://shows.acast.com/irishhistory/episodes/emily-anderson-the-forgotten-irish-bletchley-park-code-break))
* Astronomers [Henrietta Swan Leavitt](https://en.wikipedia.org/wiki/Henrietta_Swan_Leavitt), [Nancy Grace Roman](https://en.wikipedia.org/wiki/Nancy_Roman), and [Caroline Herschel](https://en.wikipedia.org/wiki/Caroline_Herschel)
```

Allow the site to re-build, and refresh the blog index.

Notice we now have two posts, but also, that the URL for our original post has changed to include its category:

```
http://localhost:4000/humour/2026/04/01/april-fools.html
```

## Accessing Category Information

Now that our posts have categories, we can use those categories in two contexts:

1. Without our `post.html` layout
2. In our blog index

### Adding the Category to the Posts Layout

Within an individual post the list of categories it belongs to is available via the `page.categories` variable. This is always an array, so when working with single categories like we are we need to remember to pipe it through the `first` Liquid filer to reduce it to a simple string.

Because I don't capitalise the categories themselves, I also pipe the value through the `capitalize` Liquid filter when using it in layouts.

We could display the current category in all sorts of ways — we could prefix it to the title, or we could add a badge after the title, but I don't like either of those options.

Instead, let's use Bootstrap's [Breadcrumb component](https://getbootstrap.com/docs/5.3/components/breadcrumb/) to visually show the post's location.

Update `./docs/_layouts/post.html` to the following:

```html
{% raw %}---
layout: default
---
<div class="post-heading mb-5">
  <h1 class="display-1 mb-0">{{ page.title }}</h1>
  <h2 class="text-muted fw-light">{{ site.meta.author }} — {{ page.date | date: "%B %d, %Y" }}</h2>
  <nav aria-label="breadcrumb">
    <ol class="breadcrumb" style="--bs-breadcrumb-divider: '>';">
      <li class="breadcrumb-item"><a href="{{ '/blog' | relative_url }}">Blog</a></li>
      <li class="breadcrumb-item">{{ page.categories | first | capitalize }}</li>
    </ol>
  </nav>
</div>

<div class="post-body">
  {{ content }}
</div>{% endraw %}
```

The only addition is the following:

```html
{% raw %}<nav aria-label="breadcrumb">
  <ol class="breadcrumb" style="--bs-breadcrumb-divider: '>';">
    <li class="breadcrumb-item"><a href="{{ '/blog' | relative_url }}">Blog</a></li>
    <li class="breadcrumb-item">{{ page.categories | first | capitalize }}</li>
  </ol>
</nav>{% endraw %}
```

Notice that I'm displaying the category name with `{% raw %}{{ page.categories | first | capitalize }}{% endraw %}`.

Allow the site to re-build, and we now have breadcrumbs at the top of each blog post showing their category.
