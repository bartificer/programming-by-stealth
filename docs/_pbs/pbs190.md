## Data Files

We've already seen that we can add any data we like into a site's configuration file (`_config.yml`), and then reference it without our site. This mechanism works great for site-wide configuration information, which is what it was intended for, but it does not scale to larger data sets.

You can make structured data available in your site by creating an optional `_data` folder and adding your datasets in supported file formats, one file per dataset.

Jekyll will accept data in the following formats:

* **JSON** — the file must be saved with `.json` file extension
* **YAML** — the file must be saved with a `.yml` or `.yaml` file extension
* **CSV** (Comma-separated values) — the file must be saved with a `.csv` file extension and **contain a header row**.
* **TSV** (Tab-separated values) — the file must be saved with a `.tsv` file extension and **contain a header row**.

When you add a file to the `_data` folder, the data within it becomes available though a key under the `site.data` object with the same base-name as the file. This means you must **never add more than one data file with the same base-name**!

If you need to add a lot of data sets you can nest your data sets in sub-folders within the `_data` folder. The you do that the folder names get added into the variable path, so a file saved in `_data/geo/climate.csv` will become available as `site.data.geo/climate`.

Data files have three advantages over hard-coding data into the site config file:

1. **Scalability** — small data sets can realistically be added straight into the config file (but you shouldn't), but that approach does not scale for larger data sets.
2. **Data Formats** — the site config file is a YAML file, but data files can be in YAML, JSON, CSV, or TSV.
3. **Watch Mode Support** — when developing locally, *watch mode* allows you to see your changes in near-real time, with one exception — configuration file changes. You need to re-start your local instance to pick up configuration changes. Data files are fully supported in watch mode, making development that little but easier.

### Worked Example — Nobel Prizes Data Set

When we explored the data querying language and command `jq` (starting in [instalment 155](./pbs155)), we made extensive use of the Nobel Prize website's JSON data set. Since we last used this data set, the Nobel Prize committee have updated [their API endpoints](https://www.nobelprize.org/about/developer-zone-2/), adding a little more information into each entry, including support for more than one language.

You'll find a snapshot of this data set exported from the free-to-use API URL `https://api.nobelprize.org/2.1/nobelPrizes?limit=1000` in the instalment ZIP file as `nobel_prizes.json`. This file was created with the following terminal command:

```sh 
curl 'https://api.nobelprize.org/2.1/nobelPrizes?limit=1000' | jq '.nobelPrizes' > nobel_prizes.json
```

Save this file into your copy of the demo site as `./docs/_data/nobel_prizes.json`.

We can now use this data within our site by looping over `site.data.nobel_prizes`.

Let's add a special page to our site to list all the Nobel Prizes ever awarded. To do this we will need a custom layout, and, a basic page that uses our new layout.

Let's start by creating the page — create `./docs/nobel_prizes.md` with the following content:

```markdown
---
layout: nobel_prizes
title: The Nobel Prizes
short_title: Nobel Prizes
date: 2026-07-20
more_info_url: https://www.nobelprize.org/about-the-nobel-prize/
---
*"The Nobel Prizes are prestigious international awards established by the will of Swedish inventor Alfred Nobel in 1895 and awarded annually since 1901. They honor outstanding achievements in physics, chemistry, physiology or medicine, literature, peace, and—since 1968—economic sciences. Each laureate receives a gold medal, diploma, and monetary prize, with ceremonies held on December 10th, the anniversary of Nobel's death. Widely regarded as the world's most distinguished recognitions, they celebrate individuals who have advanced human knowledge, promoted peace, and enriched literary culture."* — [Lumo AI](https://proton.me/lumo)
```

This file contains an editable description of what the Nobel Prizes are, and, some front matter data that our custom layout will utilise:

1. `date` — this is a standard Jekyll field that can be added to any page. It gets interpreted as the page's last-edited date, and can be accessed in layouts as `page.data` (just like all other page front matter). The date should be formatted as ISO 8601 (`YYYY-MM-DD`). We'll use this field to record the date the data set was last refreshed.
2. `more_info_url` — a URL linking to an appropriate detailed description of what the Nobel Prizes are.

Note that we are specifying a layout that does not exist yet (`nobel_prize`). This will cause a warning when the site re-builds, and the new page will initially be created using the `default` layout.

Let's now create our custom layout.

Create a file named `./docs/_layouts/nobel_prizes.html` with the following content:

```html
{% raw %}---
layout: default
---
<header class="mb-4">
  <h1 class="display-1 mb-0">{{ page.title }}</h1>
  <p class="my-0"><small class="text-muted">Snapshotted from <a href="https://www.nobelprize.org/about/developer-zone-2/" target="_blank">the Nobel Prize API</a> on {{ page.date | date: "%B %d, %Y" }}</small></p>
</header>

<div class="card mb-4 bg-info-subtle text-info-emphasis">
  <div class="card-header">
    ℹ️ About {{ page.title}}
  </div>
  <div class="card-body">
    <div class="card-text">{{ content }}</div>
    {% if page.more_info_url %}
    <a href="{{ page.more_info_url }}" target="_blank" class="card-link link-underline link-underline-opacity-0">More …</a>
    {% endif %}
  </div>
</div>

<h1>All Awarded Prizes</h1>
<dl>
  {%- for prize in site.data.nobel_prizes %}
  <dt>{{ prize.awardYear}} — {{ prize.category.en }}</dt>
  <dd class="ps-3">
    {%- if prize.topMotivation.en %}
    <p><strong>Note:</strong> {{ prize.topMotivation.en }}</p>
    {%- endif %}
    {%- if prize.laureates %}
    <ol>
      {%- for laureate in prize.laureates %}
      <li><strong>{{ laureate.knownName.en | default: laureate.orgName.en }}</strong>{% if laureate.motivation.en %} — {{ laureate.motivation.en }}{% endif %}</li>
      {%- endfor %}
    </ol>
    {%- endif %}
  </dd>
  {%- endfor %}
</dl>{% endraw %}
```

I want to draw your attention to a few details.

Firstly, this is yet another nested layout within our default layout.

Secondly, the content from the markdown file is used as the text for an information card describing what the Nobel Prizes are.

Thirdly, the prizes are rendered as an HTML definition list which is built by looping over the liquid variable `site.data.nobel_prizes`.

Finally, our layout makes use of the front matter flagged for your attention in the markdown file (`page.date` & `page.more_info_url`).

Allow the site to re-build, and you'll see we now have a complete listing of all awarded Nobel Prizes as of July 2026.

## Controlling Permalinks

Jekyll provides very sensible defaults for permalinks, but you can assert your own preferences as desired.

Firstly, you can override the permalink for any piece of content using the `permalink` front matter key.

To see how this works, let's shorten the URL for our Nobel Prize listing from its default `./nobel_prizes.html` to simply `./nobels/` by adding the following to the font matter in `./docs/nobel_prizes.md`:

```yaml
permalink: /nobels/
```

If the collection your content belongs to uses URL slugs as part of it's permalink structure, then you can override just the slug for a specific piece of content using the `slug` front matter key.

In [the previous instalment](./pbs189) we learned how to control the permalink structure for any custom collections we create. We can do the same for the built-in taxonomies *pages* and *posts* via the site configuration file.

You can update the structure for the entire site using the site-wide configuration key `permalink`. This can be useful, but it gets a little confusing to read because you need to add all your desired placeholders for pages and posts into the one template, even though some of those placeholders only exist for some types of content. A better approach is to define the permalink structure as the per-collection level using the `collections` dictionary.

To understand how this works, it's important to know that under the hood **both the _pages_ and _posts_ taxonomies are implemented as _collections_**. This means we can control their permalink structure by adding entries of the following form to the site configuration file:

```yaml
collections:
  pages:
    permalink: PATTERN_HERE
  posts:
  	permalink: PATTERN_HERE
```

The list of supported placeholders is very long, and it varies from taxonomy to taxonomy, but you'll find all the details in the [Jekyll permalink documentation](https://jekyllrb.com/docs/permalinks/).

Because certain permalink structures are very common, Jekyll provides a few named permalink styles that act as predefined combinations of placeholders. Most notably:

* `permalink: date` → `/:categories/:year/:month/:day/:title:output_ext`
* `permalink: pretty` → `/:categories/:year/:month/:day/:title/`
* `permalink: none` → `/:categories/:title:output_ext`


## Front Matter Defaults

We briefly looked at how front matter defaults in the site config file (`_config.yml`) work in [the previous instalment](./pbs189) when we used this feature to apply a specific layout to every entry in the `recipes` taxonomy. In that instalment our focus was on content collections, so we  didn't look at this useful feature in detail. Let's now re-visit the feature for a deeper description of how it works.

Firstly, [the documentation](https://jekyllrb.com/docs/configuration/front-matter-defaults/) makes it clear that every entry in the `defaults` array must define the following two top-level keys — `scope`, and `values`, both of which should be dictionaries. As well as that, the `scope` dictionary **must** define a `path` key, and *can* also add a `type` key. All other keys will be ignored. The `values` dictionary can define any key, and what ever is defined will appear in content that matches the `scope` as `page.KEY_NAME`. If a specific file containing content, i.e. one of your Markdown files, defines a different value for a key that has been assigned a default value, then the value defined in the markdown file takes precedence. In other words values defined in, `site.defaults[*].values.*` are treated like you would expect default values to be treated!

Secondly, the `scope.path` property is interpreted as a folder **within your site's source **(`./docs` in our example site), not as a path within the generate website. In other words, to apply a default to all Markdown files saved anywhere under `SITE_SOURCE_FOLDER/my_category/_posts`, you would set `scope.path` to `my_category/_posts`.

This means that **all Markdown files** saved anywhere within the site can be targeted by explicitly setting `scope.path` to **an empty string**.

The documentation also states that the `*` wild card character can be used within scopes, but warns that it can have significant performance impacts when rendering complex sites.

And finally, as we learned in the previous instalment, the `scope.type` property can be used to limit the scope to only Markdown files belonging to specific collections.

We'll see some examples of how site defaults can be used in the final worked example below.

## Worked Example — Revisiting our Metadata Headers

As a quick reminder, learned about the SEO and social media HTML metadata headers in instalment, and we added some basic metadata headers to our demo site in instalment.

We added those basic headers before adding a blog to our site, and, before adding our custom collections. We should re-visit our implementation of these headers to take account of our new, richer, information architecture.

The first header that needs some improvement is the OpenGraph page type (`<meta property="og:type">`). We need to set this to `article` for blog posts and recipes. Currently we set this header in `./docs/_includes/html_head_common.html` with the lines:

```html
{% raw %}{%- if site.meta.og_type %}
<meta property="og:type" content="{{ site.meta.og_type }}">
{%- endif %}{% endraw %}
```

There are many possible ways we could implement the desired overrides, but I'm going to use this as an opportunity to illustrate the use of the `page.collection` property.

Rather than using a single value in the site config, let's add our desired customisation directly within the snippet.

Replace the lines above with the following:

```html
{% raw %}{%- if page.collection == 'posts' or page.collection == 'recipes' %}
<meta property="og:type" content="article">
{%- else %}
<meta property="og:type" content="website">
{%- endif %}{% endraw %}
```

Since we're no longer using `site.meta.og_type`, you can delete the line `og_type: website` from `./docs/_config.yaml`.

Re-start Jekyll to be sure the updated config file is read, rebuild the site, and then you can verify that blog posts and recipes get the header:

```html
<meta property="og:type" content="article">
```

While all other pages, including the blog and recipe indexes get the header:

```html
<meta property="og:type" content="website">
```

Next, let's add some search engine keywords by defining a `<meta name="keywords">` tag.

The value for this tag should be a comma-separated list of keywords. It makes sense to build the list for a given page from a number of possible sources, specifically:

1. Any categories the item belongs to.
2. Any tags assigned to the item.
3. Any keywords defined in the item's front matter as `meta.keywords`

While the latest version of Jekyll supports the direct creation of an empty list, the version of Jekyll GitHub uses does not. However, there is a commonly used workaround that looks a little silly, but works reliably:

```html
{% raw %}{%- assign _empty_array = '' | split: ',' %}{% endraw %}
```

This creates an empty list named `_empty_array` by splitting an empty string on a comma.

We can use this empty list as the default value when building three separate initial lists of keywords, one for each supported source. Once we have our three lists, some or all of which could be empty, we can combine them into a final master list using the `concat` Liquid filter, and remove any duplicates with the `uniq` filter. If we have any keywords in our final list, we can render them as a comma-separated list with the `join` filter.

Add the following to the end of `./docs/_includes/html_head_common.html`:

```html
{% raw %}{%- assign _empty_array = '' | split: ',' %}
{%- assign category_keywords = page.categories | default: _empty_array %}
{%- assign tag_keywords = page.tags | default: _empty_array %}
{%- assign page_keywords = page.meta.keywords | default: _empty_array %}
{%- assign keywords = category_keywords | concat: tag_keywords | concat: page_keywords | uniq %}
{%- if keywords.size > 0 %}
<meta name="keywords" content="{{ keywords | join: ', ' }}">
{%- endif %}{% endraw %}
```

Allow the site to re-build, navigate to the blog post about female scientists, and view the page source. You'll see that the post's category, *science*, and tags, *scientists* & *diversity*, have all been added as keywords:

```html
<meta name="keywords" content="science, scientists, diversity">
```

Navigating to the blog listing and viewing the source shows no keywords, let's add one directly to the page's front matter.

Open `./docs/blog.md` and add the following to the end of the front matter:

```yaml
meta:
  keywords: [ blog ]
```

Allow the site to re-build, and view the updated page source. Now notice the page has one keyword:

```html
<meta name="keywords" content="blog">
```

Let's do something similar for the recipe index. Edit `./` and add the following to the end of the front matter:

```yaml
meta:
  keywords:
    - recipes
    - cooking
    - food
```

Allow the page to re-build, and view the source to reveal the expected keywords:

```html
<meta name="keywords" content="recipes, cooking, food">
```

Finally, let's use front matter defaults to add the same standard keywords to all recipes.

Edit the site config file (`./docs/_config.yml`) and find the current front matter defaults for the `recpies` collection:

```yaml
# Configure front matter defaults
defaults:
  - scope:
      path: ""
      type: recipes
    values:
      layout: recipe
```

At the moment, we have one entry that applies to all items anywhere in the site that belong to the `recipes` collection and sets just one front matter value, `page.layout` to `recipe`.

Let's add another value for `page.meta.keywords`. Replace the code above with the following:

```yaml
# Configure front matter defaults
defaults:
  - scope:
      path: ""
      type: recipes
    values:
      layout: recipe
      meta:
        keywords:
          - recipe
          - cooking
          - food
```

Re-start Jekyll and re-build the site, then navigate to our one recipe, the banana pancakes, and view the source to verify we have the expected keywords:

```html
<meta name="keywords" content="recipe, cooking, food">
```

## Jekyll Overview

Now that we're at the end of our Jekyll journey, let's quickly summarise the set of features and technologies at your disposal when building a website with Jekyll.

1. [Jekyll](https://jekyllrb.com) is a *static site generator* written in [Ruby](https://jekyllrb.com/docs/ruby-101/) that transforms a collection of source files in a defined [folder structure](https://jekyllrb.com/docs/structure/) into a rendered website using [Jekyll's rendering process](https://jekyllrb.com/docs/rendering-process/).
2. Content is added to sites using three distinct types of files
   1. Rendered files, generally written in [Markdown](https://www.markdownlang.com) (though you can use HTML if you prefer). These files should only contain content, and that content can be enriched with the [Liquid templating language](https://jekyllrb.com/docs/liquid/) and the [Jekyll Variables](https://jekyllrb.com/docs/variables/). Jekyll processes these files, wrapping them in an appropriate *Jekyll Layout*.
   2. [Static files](https://jekyllrb.com/docs/assets/), generally images or other media. These files are not processed by Jekyll in any way, and published un-changed.
   3. [Assets](https://jekyllrb.com/docs/assets/), files that support Jekyll Layouts. These files are compiled from a source language to a destination langue, the following two languages are currently supported:
      1. [SASS](https://sass-lang.com) files get compiled to CSS
      2. [CoffeeScript](https://coffeescript.org) files get compiled to Javascript
3. Metadata and [configuration information](https://jekyllrb.com/docs/configuration/) is expressed in [YAML](https://yaml.org/about/), both in the configuration file, and in [front-matter](https://jekyllrb.com/docs/front-matter/) sections at the start of rendered files.
4. A site's look is defined with nested [Jekyll Layouts](https://jekyllrb.com/docs/layouts/) written in HTML and the Liquid templating language using the Jekyll variables.
   - Enriched with static like including Javascript, CSS, images
   - Enriched with compiled assets like SASS and CoffeeScript
   -  Layouts defined by others can be imported into a Jekyll site as a [Jekyll Theme](https://jekyllrb.com/docs/themes/), and that theme can be augmented with layout and defined within the site.
5. [Jekyll Includes](https://jekyllrb.com/docs/includes/) are used to define re-usable snippets. These snippets can be used for both content and layout, and are written in Markdown or HTML and enriched with the Liquid templating engine and the Jekyll variables.
6. A site's information architecture is defined with taxonomies:
   1. Two built-in top-level taxonomies — one for [regular pages](https://jekyllrb.com/docs/pages/), and one for [dated posts](https://jekyllrb.com/docs/posts/).
   2. Two built-in sub-taxonomies for [categories and tags](https://jekyllrb.com/docs/posts/#tags-and-categories).
   3. [Jekyll Collections](https://jekyllrb.com/docs/collections/) provide custom taxonomies.
7. [Permalinks](https://jekyllrb.com/docs/permalinks/) are used to define the URL structure of the rendered site.
8. A site's content can be enriched with information stored in [data files](https://jekyllrb.com/docs/datafiles/) formatted in JSON, YAML, CSV, or TSV. 

## Final Thoughts

Static site generators in general provide a good alternative to real-time content management systems like Wordpress for sites that don't update more than a few times a day. They're much cheaper and simpler to host because the generated site is purely static, consisting of nothing more than a collection of HTML, CSS, Javascript, and image files. There's no need for server-side processing, so no need for PHP or similar server-side language, and there's no database, so need for a MySQL or PostgreSQL server.

There are lots of static site generators available, but Jekyll has the advantage of being supported out-of-the-box on GitHub, allowing for free site generation and hosting on a custom domain with [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). You can mange and host a Jekyll site as a GitHub repository, where your content is automatically versioned, and the Jekyll build process automatically triggered each time you push a change to your repository, and the generated website immediately availably online.

If you like the concept of a static site generator, but find something about Jekyll doesn't agree with you — perhaps you find Ruby app a pain to work with — [Hugo](https://gohugo.io) is an interesting alternative that is gaining popularity at the moment (summer 2026).
