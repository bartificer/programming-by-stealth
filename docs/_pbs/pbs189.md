At this point in our journey we know Jekyll has three top-level taxonomies — *pages*, *posts*, and *collections*. We've been using *pages* for our entire exploration of Jekyll, and in the previous instalment we explored how *posts* can be used to add a blog or new feed to a Jekyll site. That leave just one unexplored taxonomy — *collections*. This is Jekyll's general purpose taxonomy, and it's used to add any organised content that is not a page or a post. Because you can add what ever custom attributes you like, you can use collections to represent just about anything.

The possible uses of collections are countless and infinite, so this instalment will be an overview of the concepts rather than a complete review of everything that's possible.

## Two Kinds of Collections

Collections come in two flavours, those that are rendered, and those that aren't. By default, when you create a collection it is not rendered. That means that when you add an item to the collection **it does not get its own page**. These un-rendered collections are intended to be used within other parts of the site.

An example might be a collection of social media profiles that get included on every page.

When you define a collection you can choose to have it rendered by setting the collection's `rendered` property to `true`. These kinds of collections behave like *pages* and *posts*, each new item gets a dedicated page in your generated website. These can be used for things like profile pages, conference talks, recipes, or any other item that's not a regular page or a blog post.

To get an idea of how collections work, we'll create one of each kind, starting with an un-rendered collection, then a rendered one.

## Creating an Un-Rendered Collection — Social Media Links

Collections are defined in the site config file (`_config.yml`) under a top-level key named `collections`. You define `collections` as a dictionary, where the collection name is the key, and the collection's configuration dictionary is the value.

We want to create a collection named `socialmedia_profiles`. Rather than relying on the default value, we'll explicitly configure it not to be rendered, and we'll explicitly set the collection to sort by a front matter key of my choosing, `sort_order`.

Add the following to `./docs/_config.yml`:

```yaml
# Define site collections
collections:
  socialmedia_profiles:
    output: false
    sort_by: sort_order
```

Note that we are free to add what ever additional fields we like after the `output` and `sort_by` fields.

The name of the collection determines that name of the folder the items need to be created in — you prefix an underscore (`_`) to the name, so the folder for our `socialmedia_profiles` collection will be `_socialmedia_profiles`. Notice that this follows the pattern we've already seen with the *posts* taxonomy, which expects to find blog posts in the `_posts` folder.

We can now create entries for our social media profiles are markdown files, which can contain any mix of front matter and content. Some collections only require front matter, others only content, but most will have a mix of front matter and content in each file.

In our case, we'll only be defining front matter.

Let's add a few special media profiles to our collection to see how it works.

Create a file named `./docs/_socialmedia_profiles/mastadon.md` with the following content:

```yaml
---
sort_order: 1
service: Mastodon
handle: @bbusschots@mstdn.social
url: https://mstdn.social/@bbusschots
---
```
